Problem first

How TEAx turns one model into a resumable study

A TEAx pipeline can evaluate one typed input. A study has to evaluate many inputs without confusing a changed model, a reordered search space, a crashed write, or a policy bug with a valid scientific result.

The loop is the easy part. The hard part is preserving the meaning of every case across retries and process restarts.

TEAx solves that by giving candidate identity, model execution, interpretation, and persistence separate contracts. The runner coordinates them. The store refuses incompatible work; when a case has evidence, it commits the case only after that evidence is durable.

CandidateA validated parameter assignment with a stable positional ID.
EvidenceWhat the sealed model produced, before study policy interprets it.
AssessmentThe study policy's disposition and objective values for that evidence.
What goes wrong without these boundaries?
  • A changed package can append results to an old database and make unlike cases look comparable.
  • A crash between writing JSON and recording its row can leave partial or orphaned data.
  • A rejected constraint result can be mislabeled as a model failure.
  • A restart can rerun an already committed case unless candidate IDs and completion checks are deterministic.

The object graph

What is assembled before the first candidate runs

The runner is a coordinator with three injected collaborators. Two inputs create those collaborators: the study YAML defines the experiment, and the sealed package defines executable behavior.

Construction-time dependenciesarrows mean “constructs or supplies”
The definition determines compatibility.

Grid order, fixed values, policy, budget, schemas, strategy identity, and the package seal contribute to the lineage the store accepts.

The evaluator is prepared once.

Package loading and graph construction happen before the per-case loop. A preparation fault is therefore a study startup fault, not a failed candidate.

Why the runner uses a CandidateBridge

The strategy and validator work with plain parameter mappings. The generated pipeline expects a Pydantic model on a named entry channel. The bridge constructs exactly that typed input: {entry_channel: entry_model(**candidate)}.

The evaluator then checks the channel name and model type against the prepared pipeline entry. If that check returns an ENTRY_VALIDATION failure, the runner raises StudyBridgeDefect. That is a broken study boundary, not ordinary bad candidate data.

Compatibility: when TEAx requires a new store

TEAx refuses the existing store when semantic configuration, strategy identity, schema fingerprint, or executable fingerprint changes. Examples include reordering grid dimensions, changing a domain or fixed value, changing the policy or budget, and rebuilding the package with a different seal.

The package's filesystem location is excluded from the semantic configuration fingerprint. Moving identical sealed code does not create a new scientific lineage; changing the sealed executable does.

Inside the sealed model

The model is a channel DAG, not a list of steps

The generated pipeline routes named, typed channels between modules. A module can combine original inputs with outputs from earlier modules. One output can feed several downstream consumers.

The repository's live toy pipeline fixtureedge labels are the fields each module consumes
Fan-out preserves the original input.

The entry payload supplies dimensions to the area module, unit cost to the cost module, and budget to the constraint module. It is not consumed by the first reader.

Fan-in expresses a real dependency.

Cost cannot run until area exists. The affordability constraint cannot run until cost exists, but it also needs the original budget.

How graph execution becomes evidence
  1. The prepared evaluator accepts typed entry-channel inputs.
  2. The pipeline executor schedules modules when their required channels exist.
  3. The exit point captures selected channel values.
  4. Projection creates ModelEvidence: constraint responses, numeric outputs, evaluator provenance, and the opaque generated report.

The framework does not import the generated report class. It reads the small attribute surface it needs. This lets generated packages remain isolated from framework code.

The control flow

A proposal may be rejected before it becomes a candidate; a candidate may be skipped, fail, or complete

These outcomes are kept distinct because they answer different questions. A proposal rejected by input validation never becomes a candidate. A model that returns a failed constraint can still be a successfully completed case.

A. Admission and resumesix blocks; terminal labels sit on their branch

The candidate ID is based on position in the proposal sequence, not a hash of the values. Invalid positions leave gaps because they never become candidates. That is why grid dimension order belongs to compatibility. On resume, the strategy recreates the same sequence and the store skips IDs with committed cases.

B. Evaluation boundarywhere the failure occurs decides whether a case is written

Current strategy and runner limits
  • The CLI exposes grid search. Python callers can also use PreparedListStrategy.
  • CandidateBridge currently targets one entry channel. Multi-entry support remains open.
  • The current strategies do not adapt from observe(); the hook is present for future adaptive strategies.
  • The store lease supports one local writer on a single host. It is not a distributed scheduler.

The commit protocol

SQLite and the filesystem cannot share a transaction

Evidence can be too large for the case table, so TEAx stores canonical JSON as content-addressed files and indexes it in SQLite. The ordering below ensures a database row never points at a partial artifact.

One successful case committhe final SQLite transaction is fenced by the active lease
  1. Serialize evidence canonically and hash the bytes.Equivalent evidence gets the same SHA-256 digest. Candidate identity is deliberately absent from the evidence object.
  2. Write under the active lease's staging directory.The file is flushed and fsynced before it can become visible as a final artifact.
  3. Rename to the digest path and fsync the artifact directory.Atomic rename publishes either the complete file or nothing at the final path.
  4. Insert the case in a fenced SQLite transaction.The row references the already-durable digest. A stale runner cannot commit after losing its lease.
Crash before publish.

There may be a truncated staging file, but no final artifact and no case row. Dead-lease garbage collection removes the temp file.

Crash after publish, before case insert.

There may be a complete orphan artifact. A retry reuses its digest, and garbage collection can remove unreachable files.

Crash after case insert.

The committed case wins. Resume sees has_case(candidate_id) and does not evaluate it again, even if forensic transitions ended early.

Replicates may share bytes.

Two candidates with identical evidence can reference one artifact. Their inputs, state, and assessment remain separate case rows.

Durability scope and database schema

The store asserts SQLite WAL mode and synchronous=FULL each time it opens. The protocol is designed for process crashes on a local filesystem. It does not claim power-loss guarantees for every storage device, safe operation on NFS, or multi-host coordination.

Reading results

Inspect builds a case view from three sources

No single file contains the whole answer. The case row holds study identity and assessment. The evidence artifact holds model output. The sealed package catalog explains which source declaration produced a constraint.

The query fan-injoined in memory; evidence is memoized by digest
Evidence is reusable; assessment is study-specific.

The artifact says what the model produced. The case row says how this study interpreted it.

Constraint IDs become explainable.

The catalog maps a runtime response back to its generated source usage and predicate context without bloating every artifact.

What inspect can filter and why fingerprints stay attached

The query surface filters by parameter, numeric output, constraint response, terminal state, and disposition. The CLI prints one JSON object per line, which is pipe-friendly. The current query implementation materializes the selected CaseView list before printing it.

Every result carries the executable fingerprint. One StudyQuery reads one compatibility-bound store; it does not combine stores with different fingerprints just because their field names match.

A practical reading order for a first contribution
  1. Run or read test_cli_end_to_end.py to see the public path.
  2. Read runner.py with the outcome table above open.
  3. Follow one success into evaluator.py and one commit into store.py.
  4. Use the focused failure, crash, and compatibility tests before changing a boundary.
