TEAx repository guide

From typed domain modules to repeatable model studies

TEAx separates the mechanics of connecting and running models from the domain code that gives those models meaning. This guide follows one battery analysis through that boundary, then shows how the same runtime executes a sealed constraint package and supplies durable evidence to a study.

What problem is this repository solving?

A techno-economic analysis is assembled from models that change at different rates

A battery analysis may combine input normalization, equipment sizing, hourly dispatch, a cost model, and a financial calculation. A different analysis may use none of those implementations, while still needing the same work around them: validate inputs, connect producers to consumers, determine a legal execution order, preserve intermediate values, and write traceable results.

The original design therefore treats an analysis as a composition of functional modules with explicit typed inputs and outputs. A researcher can call a module directly in a notebook while its behavior is still being developed. Once the module boundaries are stable, the same modules can be selected and connected in YAML for an automated run. That progression matters because TEAx does not require early experiments to adopt a pipeline before their interfaces are understood.

The repository implements that split with two packages. teax-simkit owns generic execution, configuration, I/O, evaluation, and study machinery. battery-tea-demo owns battery schemas, defaults, modules, and fixtures. The framework has tests that reject battery-specific imports, so a second domain package can use the runtime without inheriting battery assumptions.

What a user supplies and receives. For an ordinary run, a user supplies typed input artifacts, a domain registry, domain schema types, and a pipeline YAML file. TEAx returns selected in-memory outputs, module-version and configuration provenance, and, by default, a run directory containing output artifacts and a manifest.

That description is still abstract. The battery demo shows how the boundary works when values begin to move.

Intent sources and present-day scope

The repository intent is recorded in the original simulation design. Current framework behavior is documented in the schema and primitive guide and the evaluation and study guide.

The current executor is serial even though configuration is represented as a dependency graph. The original design anticipates asynchronously runnable modules, but the implementation today uses a topological order in one process. The graph still provides validation and makes future scheduling choices possible without changing domain module interfaces.

What happens during one actual analysis?

A battery run turns three entry artifacts into five published results

The repository’s battery pipeline fixture starts with a geography, an 8,760-hour load profile, and financial parameters. The entry point loads each artifact into a Pydantic model and places that model on a named channel. A channel is the runtime slot through which one produced value can reach any number of downstream inputs.

modules:
  entry_point:
    module_type: EntryPoint
    inputs:
      geo: Geography ../geography_us_ca_pge.json
      load_profile: LoadProfile8760 ../load_profile_toy_8760.json
      financial_params: FinancialParams ../financial_params_demo.json

  rate_data:
    module_type: RateData
    inputs:
      geography: Geography geo
    outputs:
      root: RootModel[RateInfo] rate_info

  configure_battery:
    module_type: ConfigureBattery
    inputs:
      load_profile: LoadProfile8760 load_profile
      rate_info: RateInfo rate_info.root
      design_prefs: None -> design_pref_default
    outputs:
      root: RootModel[BatteryConfig] battery_config

The binding RateInfo rate_info.root means more than “use the rate result.” The rate_info channel contains a RootModel[RateInfo]; the binding extracts its single root field and passes the contained RateInfo to the sizing module. The validator checks that the field exists and has the exact type the registered module declares before execution starts.

At runtime, the rate module first turns geography into an hourly tariff. Battery sizing then combines the load profile and tariff, filling the omitted design preferences from domain defaults. The resulting battery configuration feeds both the hourly performance simulation and the cost calculator. The project analyzer cannot run until rate data, telemetry, cost, and the original financial parameters are all available. It uses telemetry and hourly prices to calculate annual savings, then combines that result with capital and operating cost to build cash flow and financial metrics.

InputsEntry artifacts are loaded relative to the pipeline file and parsed into declared Pydantic types before they become channels.
Intermediate valuesChannels hold the actual objects returned by modules. They remain in the per-run execution context and may have multiple consumers.
Outputs and reportsExitPoint selects channels. The returned RunResult holds them in memory; the output router writes configured artifacts and a manifest.

This example also shows why the repository needs a framework/domain boundary. The runtime can understand channel ownership, type names, and dependencies without understanding a tariff, a state of charge, or NPV. Those meanings remain in the battery package.

Which part of the repository owns each responsibility?

The domain package supplies meaning; the framework supplies execution boundaries

The framework does not discover every installed module globally. A caller creates a domain registry and passes it into execution. The registry contains factories plus the required, optional, and output types that were introspected from each module class. Pipeline YAML refers to those registered names, so changing a Python class name or a YAML module_type is a contract change unless the domain registry provides an override.

The architecture now raises a more precise question: how does YAML become an executable order while preserving the typed channel contract?

How does configuration become execution?

Validation joins YAML bindings to registered Python types before scheduling

Pipeline loading first parses each binding into a structured specification. Every non-exit output claims a channel name, and only one module may provide that channel. Inputs name either a full channel, one field on a channel, or an explicit None default. The specification requires exactly one EntryPoint and one ExitPoint.

The validator then uses the domain registry to compare configuration with code. It verifies that a module type exists, that required and optional inputs line up, that declared output fields and types match the descriptor, and that ExitPoint has a writer for every selected type. For field references, it resolves the parent channel type and checks a single public, non-computed field with an exact type match. This catches a misspelled field or a misleading type declaration before any domain module runs.

After type validation, the DAG builder maps each channel to its provider. Every consumer gets a dependency edge from that provider; ExitPoint gets edges from the providers of all selected outputs. Python’s topological sorter rejects cycles and returns a legal order. The current executor walks that order serially.

ParseYAML becomes a typed PipelineSpecification.
ResolveRegistry descriptors connect module_type names to factories and types.
ValidateInputs, outputs, fields, writers, and unique providers are checked.
BuildChannel providers become dependency and adjacency maps.
ExecuteFresh module instances read resolved channel values in topological order.
RouteExitPoint channels are returned and optionally written with a manifest.

One module can publish several independently consumed values

The battery synchronous-simulation module demonstrates the multi-output model. It returns a SyncSimOutputs container with forecasts, guidance, and telemetry. A pipeline can map those three model fields to separate channels, and downstream consumers can subscribe to only the value they need. The executor decomposes a MultiOutput with to_channel_dict(); it also retains a legacy mapping path for older multi-output modules.

synchronous_sim:
  module_type: SynchronousSim
  inputs:
    time_grid: SyncTimeGrid time_grid
    initial_state: BatteryState initial_state
    price_trajectory: PriceTrajectory price_trajectory
    forecast_config: MockForecastConfig forecast_config
    guidance_config: GuidanceConfig guidance_config
    dynamics_config: DynamicSimConfig dynamics_config
  outputs:
    forecasts: MockForecastSeries forecasts
    guidances: SyncGuidanceSeries guidances
    telemetry: SyncTelemetrySeries telemetry

That separation matters when output size and format differ. Forecasts and guidance use JSON writers, while battery telemetry can use a domain Parquet handler. The channel graph remains about typed values; the output router decides how selected boundary values become artifacts.

Exact channel and field-reference invariants
  • A specification has exactly one EntryPoint and one ExitPoint.
  • Each channel has at most one non-exit provider. Any number of modules may consume it.
  • A regular module cannot consume its own output channel.
  • Field references are one level deep. Nested, private, and computed fields are rejected.
  • Field types use exact equality after unwrapping Optional[T]; coercion is not used to make an incompatible binding pass.
  • An explicit None -> name supplies None so the module’s own validation/default logic can choose a value.
  • A single-output module places its entire returned model on the channel. A RootModel[T] therefore remains wrapped until a consumer selects .root.
  • A multi-output module publishes individual fields. Bare primitive fields may therefore appear directly on channels.

Implementation: pipeline schema, validator, DAG builder, and executor.

Output behavior and current serialization limits

ExitPoint declarations must name the actual channel type and a filename whose extension matches the registered writer. The default router handles generic framework outputs and JSON-native primitives in bare or RootModel form. Passing custom_schema_types lets execute_pipeline add JSON handlers for those domain models. An explicit router replaces that default choice and owns its entire handler set.

A missing channel value represented by None is recorded in the manifest as produced: false; it is not written as JSON null. Lists, dictionaries, bytes, Decimal, and other unregistered values require an explicit handler. See Using primitive types in TEAx modules for the full boundary contract.

Current synchronous-pipeline fixture mismatch

The checked-in synchronous pipeline fixture currently declares a fourth output field named synchronous_sim. SyncSimOutputs defines only forecasts, guidances, and telemetry, so registry validation rejects that fixture before execution. The battery integration test exercises the linear pipeline, not this YAML. A contributor making the synchronous pipeline runnable should reconcile the YAML with the output model and add an integration test for the configured run.

An ordinary pipeline run is sufficient when code, configuration, and inputs live together. Generated constraint models add another requirement: TEAx must prove which executable package produced a verdict and must avoid coupling study code to generated class names.

Why is evaluation separate from pipeline execution?

Evaluation fixes an executable package, then turns each case into runtime-owned evidence

A generated package contains its own schemas, modules, registry factory, pipeline, constraint report types, model contract, catalog, and seal verifier. TEAx does not create that package; it consumes one produced by the external code-generation workflow. The repository includes a sealed toy package as an executable fixture.

Loading begins with the package’s own standard-library verifier. The loader checks the declared package name and the sealed file set, including missing, extra, and modified files, and checks the recorded runtime contract version. It then exposes the directory under its declared import name using a link in caller-owned scratch space because generated internal imports are absolute. This is integrity and compatibility checking, not an operating-system sandbox: generated modules execute in the TEAx Python process.

PreparedEvaluator loads that verified package, obtains its registry factory and custom schema list, parses the packaged pipeline, and builds the graph once. The entry-channel model classes are derived from the pipeline specification. For every call to evaluate, the evaluator validates the supplied channel-to-model mapping and creates a fresh execution context, so channel values from one candidate cannot leak into the next.

from pathlib import Path

from simkit.evaluation import PreparedEvaluator, ProvisionalPackageLoader

package_dir = Path("generated/my_model")
loader = ProvisionalPackageLoader(
    package_dir=package_dir,
    package_name="my_model",
    link_root=Path(".teax/package-links"),
)
evaluator = PreparedEvaluator(loader, package_dir / "pipelines/pipeline.yaml")

EntryModel = evaluator.entry_models["model_params"]
evidence = evaluator.evaluate({
    "model_params": EntryModel(length=4.0, width=3.0, budget=5000.0)
})

The in-memory evaluator replaces only file-backed EntryPoint loading and disables output persistence. The rest of the real executor and graph are used. FileBackedEvaluator provides an audit-oriented alternative: it copies the pipeline specification to a scratch work directory, reads an entry JSON file, and writes normal run artifacts outside the sealed tree. A parity test requires both backends to project the same evidence.

The evidence envelope contains canonical responses, selected numeric outputs, provenance, and the generated report. Projection reads the generated report by attribute shape rather than importing a particular generated type. Provenance names the executable fingerprint, evidence and evaluator versions, and a digest of the typed inputs. This lets downstream code compare or persist results without knowing that the fixture happens to contain ToyPlantParams or a particular constraint class.

Evaluation failure semantics

Evaluation normalizes failures into four phases: entry_validation, preparation, module_execution, and output_write. The prepared in-memory path can produce the first three; output writing is part of the general taxonomy for persisting evaluators.

An indeterminate constraint verdict is evidence, not an evaluator failure. The model ran and reported that it could not produce a finite yes/no result. A study can keep such a case near a boundary while treating an exception during module execution as an execution_failed case.

Package compatibility and isolation limits

Strict loading rejects a declared-name mismatch, tampered or missing covered file, unhashed extra file, or runtime-contract mismatch. The executable fingerprint comes from the verified package contract. The fixture verifier is loaded by file path before the package itself is imported.

The evaluation envelope, entry validation, projection, and failure vocabulary have source-scan tests that prohibit generated-package imports. The loader and evaluator necessarily import and execute the package. There is no subprocess, container, resource quota, or hostile-code sandbox in this repository.

Once one case has a stable identity and evidence shape, a separate layer can propose many cases, decide what their evidence means for a search, and preserve progress across interruption.

How does TEAx move from one evaluation to many?

A study adds candidate identity, policy, and durable progress around an evaluator

A study definition binds a strategy, proposal validator, entry-model bridge, evaluator identity, and assessment policy. The built-in grid strategy enumerates a Cartesian product in the variable order written in configuration. That order is part of the strategy fingerprint because positional proposal and candidate IDs must be reproduced after a restart. A bounded wrapper can stop after budget candidates without changing the runner.

Each raw proposal is validated and canonicalized before it becomes a candidate. Invalid proposals are recorded as proposals but never become cases. For a valid proposal, CandidateBridge instantiates the generated entry model and maps it to the configured entry channel. The current bridge supports one entry channel; a package whose case spans several entry channels needs a broader bridge before it can use the study runner.

ProposeStrategy emits an ordered proposal ID and raw parameter mapping.
ValidateThe study canonicalizes numeric fields and merges fixed values.
BridgeThe mapping becomes the evaluator’s typed entry-channel input.
EvaluateThe fixed package graph produces immutable model evidence.
AssessPolicy reads evidence and returns a separate disposition.
CommitEvidence is staged, then the case row is atomically recorded.

The built-in objective policy maps a violated headline to reject, an indeterminate or unassessed headline to keep-for-boundary, and a satisfied case to feed-strategy unless a configured objective crosses its penalty threshold. Missing configured outputs or response-role constraints cause assessment_failed. That state is distinct from a policy disposition: a rejected candidate completed model evaluation and policy assessment, while an assessment failure means policy could not interpret valid evidence.

Persistence makes resume a compatibility check, not a best-effort replay

The store is a local SQLite database plus content-addressed evidence files. On creation, it binds the study ID, package fingerprint, model-contract fingerprint, study-definition fingerprint, schema versions, and strategy identity/configuration. Every later open compares all of them. Editing grid order, policy, fixed values, budget, or the sealed executable makes the existing store incompatible instead of mixing results from two lineages.

A single runner holds a fenced lease with a heartbeat. Evidence bytes are written to a lease-specific temporary file, flushed, renamed atomically to artifacts/<sha256>.json, and only then referenced by an atomically inserted case row. If a process dies before the case commit, resume sees no case and reevaluates that candidate; an orphan artifact may remain until garbage collection. If the case exists, has_case skips it. Crash tests compare the resumed case sequence and evidence digests with an uninterrupted reference run.

Recorded resultMeaningEvidence artifact
completedEvaluation and policy both returned. The assessment carries reject, penalize, keep-for-boundary, or feed-strategy.Present
execution_failedA module-execution or output-write phase failed. The case stores normalized failure data.Absent because no complete evidence was produced
assessment_failedThe model produced evidence, but policy could not extract or interpret configured information.Present and preserved unchanged

Querying reverses the storage boundary without re-running the model. StudyQuery reads committed cases, decodes each evidence digest once, and joins constraint IDs through the package catalog to source usage and source records. Every view carries the executable fingerprint. The query intentionally does not merge results across model versions; an optional tracking key can name a logical constraint across versions, but a caller must perform and display that cross-fingerprint comparison.

The store requires local-filesystem SQLite with WAL and synchronous=FULL, asserted on open. Its tested claim is killed-process recovery. It does not claim power-loss safety or network-filesystem correctness.

Study limitations in the current implementation
  • The CLI builds a prepared in-memory evaluator and a single-channel CandidateBridge.
  • Built-in strategies are prepared lists and ordered grids. Their observe methods are inert; adaptive optimization is not implemented.
  • The built-in policy classifies and records feed-strategy, but current strategies do not adapt to that feedback.
  • The query loads case views eagerly and joins the package’s current constraint-catalog shape.
  • A study is bound to one executable fingerprint. Cross-store, cross-version correlation is left to a caller.
  • The single-run battery demo and generated-package study fixture are separate examples; the CLI is currently shaped around sealed generated packages.

Which interface should an engineer use?

Choose the boundary that matches the work

Develop one domain calculation

Instantiate a module and call validate_and_fill_default or run with typed models. This keeps a notebook experiment close to the domain code.

Run one configured domain analysis

Call execute_pipeline with YAML, a domain registry, and domain schema types. This is the primary public surface for the battery pipeline.

Evaluate one sealed generated model

Construct PreparedEvaluator for repeated in-memory cases or FileBackedEvaluator when a normal artifact trail is required.

Run and resume many generated-model cases

Use the teax-study CLI or assemble StudyDefinition, StudyStore, and StudyRunner in Python.

Run the checked battery pipeline from Python

There is no general pipeline console command in the current package. The supported repository example calls the Python function and supplies the battery registry and every domain type carried at the entry or exit boundary.

from pathlib import Path
from pydantic import RootModel

from battery_tea import create_battery_registry, schemas
from simkit.config import schema as generic
from simkit.core.pipeline import execute_pipeline

result = execute_pipeline(
    Path("packages/battery-tea-demo/battery_tea/tests/fixtures/"
         "pipeline_configs/demo_linear_alt.yaml"),
    output_dir=Path("run_data/outputs"),
    registry=create_battery_registry(),
    custom_schema_types=[
        schemas.Geography,
        schemas.LoadProfile8760,
        schemas.RateInfo,
        schemas.BatteryConfig,
        schemas.BatteryTelemetry8760,
        schemas.CostBreakdown,
        schemas.RateInfoOutput,
        schemas.BatteryConfigOutput,
        schemas.BatteryTelemetry8760Output,
        schemas.CostBreakdownOutput,
        RootModel[generic.FinancialResults],
    ],
)

financial_results = result.outputs["financial_results"].root
print(financial_results.npv)
print(result.manifest)

Add a typed module to a domain package

A module names its input and output models in the generic base class and returns ModuleResult. create_registry introspects those types and the run signature. A domain registry may override the class name with the stable string used in YAML.

from pydantic import BaseModel
from simkit.core.base import ModuleBase, ModuleResult
from simkit.core.registry_builder import create_registry

class LossInputs(BaseModel):
    energy_kwh: float
    efficiency: float

class LossOutput(BaseModel):
    lost_kwh: float

class LossModule(ModuleBase[LossInputs, LossOutput]):
    name = "loss"
    version = "v1.0"

    def validate_and_fill_default(self, energy_kwh: float, efficiency: float) -> LossInputs:
        return LossInputs(energy_kwh=energy_kwh, efficiency=efficiency)

    def run(self, energy_kwh: float, efficiency: float) -> ModuleResult[LossOutput]:
        inputs = self.validate_and_fill_default(energy_kwh, efficiency)
        return ModuleResult(LossOutput(
            lost_kwh=inputs.energy_kwh * (1.0 - inputs.efficiency)
        ))

registry = create_registry([LossModule])

Describe and drive a study

The study config names the sealed package, the entry boundary, an ordered grid, fixed generated-model fields, and an evidence policy. Paths below are illustrative, while the field and interface shapes match the checked end-to-end fixture.

study_id: toy-grid-demo
package:
  dir: generated/wi014_s4
  name: wi014_s4
  spec: pipelines/pipeline.yaml
entry_channel: toy_plant_params
entry_model: ToyPlantParams
grid:
  - [toy_plant__Toy_Plant__plant_budget, [1000.0, 3000.0, 6000.0]]
fixed:
  toy_plant__Toy_Plant__plant_length: 4.0
  toy_plant__Toy_Plant__plant_width: 3.0
  toy_plant__Toy_Plant__plant_unit_cost: 250.0
policy:
  name: objective/v1
  objectives:
    - output: toy_plant__demo_plant__cost_calc__cost
      role: minimize
  response_roles: {}
budget: null
retention: keep
# Bind a new SQLite store to this exact package and study definition.
teax-study create --config study.yaml --store results/study.db

# Enumerate candidates, evaluate, assess, and commit each result.
teax-study run --config study.yaml --store results/study.db

# Rebuild the same definition, reject incompatibility, and skip committed cases.
teax-study resume --config study.yaml --store results/study.db

# Emit one JSON object per matching committed case.
teax-study inspect --config study.yaml --store results/study.db \
  --state completed --disposition reject

run is already idempotent for committed candidate IDs, while resume uses the same implementation and communicates lifecycle intent. inspect also accepts --parameter, --output, and --constraint presence filters. Its JSON includes inputs, numeric outputs, per-constraint verdicts, catalog details, disposition, evidence digest, and executable fingerprint.

Where should a contributor begin?

Start from the contract you intend to change

A useful reading path follows one value rather than reading package directories alphabetically. For ordinary pipelines, begin with the battery integration test and its YAML, then follow the call into execute_pipeline, validation, the DAG builder, and the executor. For generated models, begin with evaluator parity and isolation tests before opening study code. For persistence, begin with crash-regime tests and then read the store’s commit order.

Where are pipeline graphs built?

simkit/core/pipeline_graph.py maps channel providers to dependency edges and calls TopologicalSorter.

Read with simkit/tests/test_toy_pipeline.py.

Where are channel bindings validated?

config/pipeline_schema.py parses binding syntax; core/pipeline_validator.py joins it to registered types.

Contracts: field-reference tests and exit tests.

How are modules registered and run?

module_introspector.py derives metadata; registry_builder.py creates descriptors; pipeline_executor.py resolves inputs and publishes outputs.

Contracts: introspection, registry, and multi-output execution.

Where does a domain add behavior?

battery_tea/schemas.py defines domain payloads; battery_tea/modules/ holds calculations; battery_tea/registry.py exposes them to YAML.

Start with the battery integration test and module tests.

Where is generated-package integrity enforced?

evaluation/package_load.py invokes the packaged verifier and imports under the declared name.

Contracts: package-load tests and isolation tests.

Where is one case evaluated?

evaluation/evaluator.py prepares and runs; evaluation/projection.py creates runtime evidence.

Contracts: prepared evaluator, backend parity, and failure taxonomy.

Where are study outcomes committed?

study/runner.py fixes candidate order and failure routing; study/store.py stages evidence and commits cases.

Contracts: runner matrix, crash regimes, and lease tests.

Where are studies configured and queried?

study/config.py rebuilds definitions; study/policy.py assesses evidence; study/query.py joins results; study/cli.py exposes the lifecycle.

Contracts: CLI resume, policy, and query.

Deeper reading paths by proposed change

Add a domain module. Read the closest battery module, its unit test, the domain registry, and the integration YAML. Keep domain validation and defaults beside the domain module. Add framework code only if the existing typed-channel contract cannot express the connection.

Add a new boundary type or file format. Read output_router.py, readers.py, and the I/O tests. Check both entry loading and ExitPoint writing; support on one side does not automatically add the other.

Change graph semantics. Read schema validation, registry validation, DAG construction, and executor tests together. A new binding form must have a parser, a static type rule, a dependency rule, and runtime resolution behavior.

Change generated-package evaluation. Read the completed evaluator spec and design, then verify the present code. Preserve the rule that evaluation’s runtime-owned modules do not import model-specific generated classes.

Change study durability or resume. Read the completed store/runner spec and design, followed by crash tests. Commit ordering, compatibility fields, candidate identity, and lease fencing form one proof and should not be changed independently.

Tests that protect the framework/domain separation

test_no_battery_deps.py checks that core exports, schemas, defaults, readers, and writers do not regain battery concepts. test_custom_schema_registration.py checks that external Pydantic types can enter the framework through the public registration path. These tests are the first place to look when a proposed convenience import seems to require a domain type inside simkit.

The practical dividing line is now visible. If a change alters what a battery value means, it belongs in the battery package. If it alters how any typed value is registered, connected, scheduled, loaded, or written, it belongs in the framework. If it alters one sealed model’s evidence boundary, begin in evaluation. If it alters candidate identity, policy, resume, or durable results, begin in study.
