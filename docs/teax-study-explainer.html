From model logic to a trustworthy study

Run the model once. Then search it safely.

Techno-economic analysis is rarely one calculation. Inputs move through several models, each candidate must be checked against constraints, and a serious study may evaluate the same pipeline hundreds of times. TEAx gives that work typed boundaries, repeatable execution, durable evidence, and a safe way to resume after interruption.

The core question TEAx makes answerable

For this candidate design, what did the model compute, which constraints held, which study decision followed, and can we prove those results belong together?

02 / mental model

Four layers. One chain of trust.

Read the architecture as a zoom lens. The pipeline computes. The evaluator turns one run into stable evidence. The study decides which cases to try and how to interpret them. The store and query surface make the history durable and useful.

Typed pipeline

Composes domain modules into a validated DAG. One entry payload moves through named, typed channels to declared outputs.

produces → RunResult

Model evaluator

Verifies a sealed generated package, prepares its graph once, and projects one case into runtime-owned evidence.

produces → ModelEvidence

Study engine

Proposes candidates, builds typed inputs, evaluates them, and applies a study policy in one fixed order.

produces → assessed case

Store + query

Commits evidence crash-safely, prevents mixed lineages, resumes idempotently, and joins verdicts to readable constraint context.

exposes → CaseView / JSONL

The boundary between layers is a data contract, not shared internal state.

03 / primary interface

Run a study in five moves.

The main external surface is teax-study. It reads a declarative YAML file, loads a sealed generated model package, and binds one SQLite store to that exact model and study definition. The same config is required again for run, resume, and inspect.

Install simkit

Install the framework so the teax-study console script is available.

Bring a sealed package

Point at a generated package containing a pipeline, schemas, contract catalog, and seal.

Describe the search

Declare an ordered grid, fixed values, objective policy, budget, and retention.

Create, then run

Bind the store first. Run or resume candidates under a single-writer lease.

Inspect JSONL

Filter cases by parameter, output, constraint, state, or disposition.

study.yaml

The study definition is executable intent.

The ordered grid is part of identity. Fixed fields complete the entry model. The policy names which outputs matter and how satisfied cases should feed the search.

example study configuration 
study_id: plant-budget-grid
package:
  dir: ./generated/plant_model
  name: plant_model
  spec: pipelines/pipeline.yaml

entry_channel: plant_params
entry_model: PlantParams

# Ordered [field name, domain] pairs
grid:
  - [plant_budget, [1000.0, 3000.0, 6000.0]]
  - [plant_width,  [2.0, 3.0]]

fixed:
  plant_length: 4.0
  unit_cost: 250.0

policy:
  name: objective/v1
  objectives:
    - { output: cost, role: minimize }
  response_roles: {}

budget: null
retention: keep
terminal

One config. Four explicit verbs.

create establishes lineage. run does work. resume repeats the same deterministic sequence and skips committed candidates. inspect is read-only.

CLI quick start 
# Development install
pip install -e packages/teax-simkit

# Bind a new store to this model + study definition
teax-study create --config study.yaml --store runs/plant.db

# Evaluate the declared candidate sequence
teax-study run --config study.yaml --store runs/plant.db

# Safe after interruption; already committed cases are skipped
teax-study resume --config study.yaml --store runs/plant.db

# One CaseView per JSON line; filters can be combined
teax-study inspect --config study.yaml --store runs/plant.db \
  --state completed --disposition feed-strategy
Why create is separate

The store records the executable, model contract, study definition, schema versions, and strategy identity at creation. A changed config or package is refused later instead of silently mixing results. Point at a new store to begin a new lineage.

Configuration field guide
  • packagedir locates the sealed tree, name is its declared import name, and spec locates the pipeline inside it. Moving the directory does not change study identity; changing the package seal does.
  • entry_channel + entry_modelName the pipeline channel to populate and the model class exported by the loaded package. Grid and fixed fields are validated into this model before evaluation.
  • gridA list of [field, domain] pairs, intentionally not a mapping. Declaration order controls row-major candidate order and is fingerprinted.
  • policyobjective/v1 extracts named scalar outputs. Satisfied cases feed the strategy unless a configured threshold says to penalize them; violated cases are rejected; indeterminate cases are retained at the boundary.
  • budget + retentionAn optional budget caps the candidate sequence and becomes part of identity. gc_after collects unreferenced staged artifacts after a run; committed evidence stays referenced.

04 / layer one

The pipeline computes one case.

The original TEAx foundation remains the engine underneath studies. A YAML specification wires small domain modules into a directed acyclic graph (DAG). Typed channels make every handoff explicit, and entry/exit points define the boundary of the model as a whole.

FILES / VALUES EntryPoint

Validates that required inputs exist and loads them into declared channels.

TYPE + NAME Typed channels

Carry immutable Pydantic models or supported primitives between modules.

INPUT → OUTPUT Module DAG

Runs functional modules in topological order with validated bindings.

DECLARED SURFACE ExitPoint

Selects channels to expose and, in normal pipeline mode, persist.

RESULT + ORIGIN RunResult

Returns outputs, module versions, a config hash, manifest, and provenance.

Core module contract

Small pieces with strict edges.

A module declares typed input and output models, validates and fills defaults, then runs. The internal algorithm can evolve without changing its neighbors as long as the boundary contract remains true.

Why it matters to studies

The whole pipeline becomes one model.

Once EntryPoint and ExitPoint describe its external shape, the evaluator can treat the graph as a repeatable function for each candidate.

05 / layer two

The evaluator makes one run comparable.

A raw pipeline result is specific to its generated model. The evaluation layer creates a stable runtime-owned envelope around it. This is the key translation: typed model input in, immutable evidence out.

01 / verify

Load the sealed package

Verify declared name, covered file hashes, extras, missing files, and runtime contract compatibility before import.

trust the executable
02 / prepare

Build the graph once

Resolve schemas, registry, entry types, output handlers, and pipeline topology before any case loop begins.

fail early
03 / evaluate

Run in a fresh context

Each candidate gets a new execution context, so channels from one case cannot leak into the next.

isolate cases
04 / project

Emit ModelEvidence

Normalize constraint responses, select numeric outputs, stamp provenance, and retain the generated report unchanged.

compare results
Invariant that matters

The evaluator does not import a specific generated report class. It reads only a small duck-typed surface: report headline and results, plus each result’s constraint ID and status. Future generated packages can change their internal classes without coupling TEAx to them.

What exactly is ModelEvidence?
  • responsesConstraint ID to satisfied, violated, or indeterminate, plus reserved key headline. The aggregate may also be not_assessed.
  • outputsSelected scalar numeric outputs unwrapped into ordinary floats. These are the values a study policy can name as objectives.
  • provenanceExecutable fingerprint, evidence schema version, evaluator version, and canonical input digest. Study and candidate IDs are deliberately excluded because the runner owns them.
  • reportThe generated constraint report retained as an opaque object. Projection attaches it unchanged.

Prepared versus file-backed evaluation
FAST PATH

PreparedEvaluator

Accepts already-typed in-memory entry models and captures outputs in memory. It loads the package and builds the graph once, then creates a fresh context per case. This is the study backend.

AUDIT PATH

FileBackedEvaluator

Copies the pipeline spec into owned scratch space, reads entry JSON, and persists normal pipeline outputs. It leaves a file trail without writing into the sealed package tree.

A parity test requires both paths to agree. That test licenses the faster in-memory path for normal studies while preserving a slower audit backend when a per-case file trail is needed.

Compare both evaluators →

Evaluation failures versus model verdicts

Failures are classified by where the machinery failed: entry_validation, preparation, module_execution, or output_write. An indeterminate constraint is different. The machinery succeeded, but the model could not produce a finite answer. It is valid evidence and remains searchable.

Rule of thumb

If the model ran and said “I cannot determine this constraint,” preserve the answer. If the execution machinery broke, route a failure.

Current search strategy

Deterministic grid, row by row.

GridStrategy computes a Cartesian product in the order variables and domain values were declared. The same config emits the same positional sequence across fresh processes. An optional bound creates a distinct study lineage.

Current policy

Evidence becomes a disposition.

objective/v1 extracts configured outputs and maps the headline to reject, penalize, keep-for-boundary, or feed-strategy.

What happens to invalid, failed, and completed work?
Invalid proposal

Recorded as a proposal only. It never becomes a candidate or case, because no canonical model input existed.

Execution failed

Module or output execution failed. The terminal case stores failure detail and has no evidence digest.

Assessment failed

Evaluation produced real evidence, but the configured policy could not interpret it. Both facts are preserved.

Completed

Evidence and policy assessment both succeeded. The case carries one of four dispositions.

Preparation faults and bridge defects fail loudly instead of becoming ordinary cases. They indicate a broken study definition or integration boundary, not a candidate-specific outcome.

Policy mapping and objective rules
  • violatedDisposition is reject.
  • indeterminate / not_assessedDisposition is keep-for-boundary. These cases carry useful information about the model’s evaluable boundary.
  • satisfied, within thresholdDisposition is feed-strategy. Objective values remain raw and available to the next search layer.
  • satisfied, beyond thresholdDisposition is penalize. The assessment records the raw penalty value.
  • Missing configured output or responseThe policy raises AssessmentFailed. Evidence stays intact and the case records assessment_failed.

07 / layer four

The store protects the meaning of a result.

Durability is more than “the database did not disappear.” A trustworthy study must not mix two model versions, expose half-written evidence, let two runners race, or duplicate completed candidates after a crash. StudyStore makes those promises explicit.

01 / lineage

Compatibility binding

The store is permanently bound to fingerprints for the executable, contract, study definition, schemas, and strategy.

prevents mixed datasets
02 / writer

Fenced single-runner lease

One live runner writes at a time. A reclaimed lease gets a new identity, so the old writer can no longer commit.

prevents races
03 / evidence

Content-addressed staging

Evidence is fully written and synced before atomic rename. The case references it only after the final file exists.

prevents partial reads
04 / resume

Candidate idempotency

Committed candidates are detected and skipped. Re-running the same sequence does not duplicate logical cases.

makes resume safe
Durability boundary

The store is crash-safe for a killed process on a single host using a local filesystem. SQLite runs in WAL mode with synchronous=FULL. The implementation does not claim power-loss safety or network-filesystem safety.

The artifact commit protocol, step by step
1 / ENCODE Canonical bytes

Encode evidence once and compute its SHA-256 digest from those exact bytes.

2 / STAGE Lease-owned temp

Write under the active lease’s staging directory and fsync the file.

3 / PUBLISH Atomic rename

Rename to artifacts/<digest>.json, then sync the directory.

4 / COMMIT Case transaction

Insert the case and artifact reference in one fenced database transaction.

5 / CLEAN Collect orphans

GC can remove staged files left by dead leases and unreferenced final artifacts.

A reader can see a durable artifact without a case if the process dies just before commit; that artifact is harmless garbage. A reader must never see a committed case pointing at a missing or half-written artifact.

How query turns stored bytes back into useful results

StudyQuery walks cases in commit order, decodes each evidence digest once, and joins each constraint verdict through the package catalog: constraint_id → source_usage → source_record. That adds the authored predicate, owner, definition, membership kind, and negation flag without changing the evidence itself.

Fingerprint boundary

A constraint ID is scoped to one executable fingerprint. TEAx does not automatically merge results across model versions. Optional tracking keys may correlate a logical subject by name, but they do not make two versioned predicates identical.

08 / data contracts

Every object has one job.

The cleanest way to understand TEAx data is to ask who is allowed to say what. Candidate input, model evidence, policy assessment, and query presentation are separate because each comes from a different authority.

01 StudyConfig

Declares which package, entry model, search space, policy, budget, and retention make up the study.

owned by operator
02 Typed entry model

Represents one canonical candidate in the exact input shape the prepared pipeline expects.

owned by package
03 ModelEvidence

Records what the model said: verdicts, selected outputs, provenance, and its opaque report.

owned by evaluator
04 Assessment + CaseRecord

Records how this study interpreted the evidence and which terminal execution state occurred.

owned by study
05 CaseView

Combines a stored case with decoded evidence and catalog context for humans and downstream tools.

owned by query
Separation that matters

A policy cannot rewrite model evidence. The evaluator cannot stamp a study decision. The query cannot merge model lineages. Those limits keep “what the model reported,” “what the study decided,” and “how a result is displayed” independently auditable.

Identity: proposal, candidate, attempt, case, and evidence digest
  • Proposal IDNames one positional raw proposal from the deterministic strategy sequence, including invalid proposals.
  • Candidate IDNames one valid canonical candidate by study and sequence position. Invalid proposals never receive one.
  • Attempt IDNames one execution attempt for a candidate. Retryable store faults can produce multiple attempts without multiple cases.
  • Case recordThe single committed terminal result for a valid candidate: completed, execution failed, or assessment failed.
  • Evidence digestThe content address of canonical evidence bytes. Identical evidence can share an artifact without collapsing distinct candidates.
Compatibility: what forces a new study lineage?

A store compares all compatibility fields exactly: study ID, executable fingerprint, model-contract fingerprint, semantic study-definition fingerprint, input/evidence schema versions, strategy identity, and strategy config fingerprint. Changing any one means the old store cannot be reopened through the normal workflow.

Package location is deliberately excluded from the semantic definition. Relocating the same sealed bytes is operational, not scientific. The executable seal captures the identity that matters.
